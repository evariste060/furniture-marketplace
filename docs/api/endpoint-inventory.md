# Backend API Endpoint Inventory

This inventory reflects the FastAPI routers currently registered by `backend/app/api/v1/router.py` and `backend/app/api/root.py` and their handlers. It describes code present in this repository, not Trello completion, release readiness, or manual QA. All application API paths use the `/api/v1` prefix. Interactive and generated API descriptions are available at `/docs`, `/redoc`, and `/api/v1/openapi.json`; these are FastAPI documentation routes, not business API endpoints.

"Implemented" means a handler is registered and has application behavior. Test references identify nearby automated coverage; they do not claim every response path has been exhaustively tested. There are no registered-but-nonfunctional application endpoints in the routers inspected.

## Errors and pagination

Every error response is `{"error": {"code": ..., "message": ..., "details": ...}}`. `code` is a stable machine-readable value (for example `not_found`, `validation_error`, `email_taken`, `insufficient_stock`, `invalid_transition`, `rate_limited`, `database_unavailable`); `message` is safe to display. Validation errors (422) use `code: "validation_error"` and list `{type, loc, msg}` entries in `details`, never the submitted values. `WWW-Authenticate` (401) and `Retry-After` (429) headers are kept. Unexpected failures return 500 `internal_error` with no internal detail.

Every paginated list returns `{"items": [...], "total": N, "page": P, "size": S}` and accepts `page` (from 1) and `size` (1–100, default 20).

## Checkout and customer orders

Module 14 (TC-06, TC-07, TC-13, TC-14; RE-026; §7 Q11–Q16, Q21). Checkout turns the caller's cart (customer bearer session or guest `X-Cart-Token`) into an order in one transaction: lines repriced from the database, the promotion re-checked and its use recorded under its row lock, delivery from the address district (free at the threshold, on the subtotal after discount; never discounted), total = subtotal − discount + delivery, VAT 18% extracted into `tax_total` (`vat_inclusive`), stock reserved. Requests carry no amounts (422). Holds: mobile money 15 minutes, cash on delivery 24 hours unless staff confirm first; an expired hold cancels the order (`payment_timeout`).

## Staff order fulfilment

Staff request bodies are strict: status update is `{"status": <known status>, "reason": <optional, up to 500 characters>}` (the reason is kept in the status history and audit record); assignment is `{"staff_user_id": <UUID>}`. Staff responses use `OrderFulfilmentResponse` (`id`, `order_number`, `status`, `fulfilment_assignee_user_id`, `created_at`, `updated_at`); the customer response omits the staff assignment identifier. Missing orders return 404, disallowed/stale transitions or incompatible inventory return 409, malformed requests return 422, and unauthenticated/unauthorized calls return 401/403. Successful updates write order status history or the current assignee and a shared `audit_records` event in one transaction. Permission denials use the existing `auth.access_denied` audit event.

## Staff category and brand management

Module 5 (RE-018). Every route needs a valid bearer session and `catalog:manage` (administrator and sales); other staff roles and customers get 403 `permission_denied`. Rules:

- Slugs are generated from the name unless one is sent: lowercase ASCII, single hyphens, and the smallest free `-2`, `-3`, ... suffix on collision. An explicitly sent slug must be unused (409 `slug_taken`). A rename keeps the slug.
- A category cannot be moved under itself or any of its subcategories (409 `category_cycle`). An unknown `parent_id` is a 422 field error.
- Category hierarchy (approved 2026-11-16): the tree has two levels, main category then subcategory. A `parent_id` must be a main category, and a category that has subcategories cannot be given a parent (422 field error on `parent_id`). Trees deeper than that, created before the cap, keep working.
- `PUT /staff/categories/order` sets `sort_order` to 1, 2, 3, ... for the categories under one parent (or the main categories), in the order sent. The list must hold every one of them, hidden ones included, exactly once; otherwise 409 `category_order_mismatch` (for example after a concurrent change). A repeated category is a 422.
- DELETE works only for unused rows. A category with products or subcategories returns 409 `category_in_use`, and a brand with products returns 409 `brand_in_use`; `details` holds the counts. Deactivate with `is_active=false` instead.
- Every successful change is audited (`catalog.category_create`, `catalog.category_update` with old and new values, `catalog.category_delete`, `catalog.category_reorder` with the positions that changed (entity ID: the parent, or `top-level`), and the same for `catalog.brand_*`). A request that changes nothing writes no audit record.
- The staff lists (`GET /staff/categories`, `GET /staff/brands`, `catalog:read`) include hidden categories and brands. Each staff category has `menu_brand_ids`, its menu brand list in order (hidden brands included).
- Brand categories (ADR-012 decision 9, 2026-11-17): each staff brand has `category_ids`, the main categories it belongs to, in menu order (empty only for a brand not linked yet). Moving a main category under another moves its brands to that main category; deleting a category removes its links. `PUT /staff/categories/{id}/menu-brands` links every listed brand to that category, and a brand update cannot remove a category whose store menu lists the brand (422 on `category_ids`). - Menu brand lists (ADR-012 decision 8, 2026-11-16): a main category's ordered list of brands for the storefront's "All Categories" menu, shown even before the brand has products there. Deleting the category or the brand removes it from lists.

## Staff product image management

Module 7. Every route needs a valid bearer session and `catalog:manage` (administrator and sales); other staff roles and customers get 403 `permission_denied`. Rules:

- Uploads are `multipart/form-data` with `file` and optional `variant_id` and `alt_text`. The file is identified by decoding it with Pillow, never by its name or declared content type; only JPEG, PNG and WebP are accepted (422 otherwise, also for corrupt files).
- Uploads over 5 MB get 413 `file_too_large`. The whole request is limited while it is received (`app/core/upload_limit.py`), and the file itself is checked against exactly 5 MB. The request limit runs before authentication, so a request over 5 MB + 64 KB gets 413 even without a token; within the limit, authentication and permissions are checked first (401/403) and nothing is processed or stored.
- Other errors: 404 `product_not_found` / `image_not_found`; 409 `sort_order_full` when the product's highest `sort_order` is already 2147483647; 422 `validation_error` for a malformed ID, an invalid file, a variant of another product or an empty PATCH. A failure while writing files gives 500 `internal_error`, with no row and no file left behind. OpenAPI (`/docs`) shows request, response and error examples for each route; FastAPI drops `null` values from those examples, so a missing `details` means `null`.
- ADR-009 (2026-10-25): the exact upload is kept in `MEDIA_ROOT/private` (never served). The public source, in `MEDIA_ROOT/public`, keeps the upload's format and is reduced to its first frame, turned upright using its EXIF orientation, stripped of all metadata and scaled down only when its longest side is above 2400 px; JPEG and WebP at quality 92, PNG losslessly. Transparency is kept for PNG and WebP. There are no thumbnails or other variants: resizing happens at delivery.
- Keys are generated server-side: `products/<product id>/<32 hex>-<12 hex>.<ext>` (the hex suffix is the start of the original's SHA-256). Public URLs are `IMAGE_PUBLIC_BASE_URL` + key. Only in development does the API serve `MEDIA_ROOT/public` itself, at `/media` (the module 7 layout is no longer served, 2026-10-26). Outside development the API refuses to start unless `IMAGE_PUBLIC_BASE_URL` is a public `https://` URL, and a web server or CDN must serve it (`docs/deployment/media.md`; not configured yet, ADR-004).
- The response keeps `thumbnail_url` for one release; it equals `url` and is marked deprecated in OpenAPI (the frontend loader requests the width it needs from `url`).
- Every stored file is tracked in the media registry (`media_objects`; ADR-009 §6, 2026-10-26). The module 7 layout and its `/media` fallback were removed.
- `variant_id` must be a variant of the same product (422); inactive variants are allowed. A new image goes after the product's highest `sort_order`; PATCH may set any value of 0 or more that no other product image of the product has (409 `sort_order_taken`; one product image per position since 2026-10-26, so `<slug>__<n>` names one image; variant images are not affected).
- Every successful change is audited (`catalog.image_upload`, `catalog.image_update` with old and new values, `catalog.image_delete`); a request that changes nothing writes no audit record.
- An upload registers its two files as pending, writes them, then links them in the transaction that adds the row; if that fails (database or audit error), the files and their registry rows are discarded. A delete removes the row and retires its files in one transaction; the cleanup worker (`python -m app.worker`) deletes them afterwards, so the API never deletes files inside a request.

The homepage hero: English and Kinyarwanda title (required, at most 80 characters), optional overline (at most 40, the small line above the title; added 2026-10-27, migration `c6f2a8d4e1b9`), subtitle (at most 160) and call-to-action label (at most 30; both languages required with a CTA URL), an on-site CTA URL, one image (media registry, owner `banners`), a position, an active flag and an optional window. Text is plain text (control characters removed; the storefront renders it as text, never HTML). The CTA URL must start with a single `/` and use only `A–Z a–z 0–9 - . _ ~ / % ? = & #`, at most 200 characters; it is percent-decoded once and checked again, so `//`, `/\`, backslashes, whitespace, control characters and schemes are refused, encoded or not. `starts_at`/`ends_at` are Africa/Kigali time without an offset, stored in UTC, shown in Kigali time. A banner is created inactive; activating it needs an image, and the image of an active banner cannot be removed (409 `banner_needs_image`). The storefront shows the first banner by position, or its default hero (copy from `messages/en.json` and `messages/rw.json`) when none is shown; no carousel. Staff routes need `content:manage` (administrator, management); every change is audited with before and after values (`content.banner_create`, `content.banner_update`, `content.banner_delete`, `content.banner_image_upload`, `content.banner_image_delete`).

## Staff catalogue import

Module 8 (TC-15). Every route needs a valid bearer session and `catalog:manage` (administrator and sales); other staff roles and customers get 403 `permission_denied`. The file schema, row rules and error semantics are in [catalogue-import.md](catalogue-import.md). In short:

- CSV (UTF-8) or XLSX, at most 10 MB and 5,000 data rows, processed within the request. One row per SKU; SKUs are created or updated, and products are found by `product_slug` and categories and brands by slug.
- Every row is checked first; valid rows are applied in one transaction and invalid rows are reported by row number and column (at most 1,000 stored errors, `errors_truncated` when cut; `error_rows` counts all).
- 201 returns the job: `completed`, or `failed` when the file is unusable (nothing changed). 422 for a missing, empty or unsupported file and 413 over 10 MB; no job is created for these. An unexpected error rolls every change back, marks the job `failed` and answers 500.
- Audited: one `catalog.import` record per job, plus the module 6 product and variant records for each change.

## Cart

Module 11 (TC-05; plan §5 and §7 Q10; RE-026 B7; security decisions in ADR-008). Owner:
- **With a bearer session:** the caller is a customer (staff-flagged accounts get 403 `customer_only`; an invalid token gets 401). X-Cart-Token is then ignored except by merge.
- **Without one:** a guest identified by `X-Cart-Token`. The guest's first `POST /cart/items` creates the cart and returns `cart_token` once; `GET /cart` without a token returns an empty cart and creates nothing.

Credentials stay in headers (`X-Cart-Token`, `Authorization: Bearer`; ADR-008 S2, approved 2026-10-24) and must never appear in URLs or logs; where the storefront stores them is still open (ADR-006). An unknown, expired or merged guest token gets 404 `cart_not_found`; another owner's line gets the same 404 `cart_item_not_found` as a line that does not exist.

Lines hold 1–99 units and never more than is available. Each line also returns `product_id` (the cart's "Save for later" moves it to the wishlist), `image` (the variant's first image, else the product's; frontend phase 4) and `previous_unit_price`: the price it was added at (`cart_items.price_at_add`, set on add and top-up, carried by merge) when that differs from today's price, with `has_price_changes` on the cart, until `POST /cart/accept-prices` (owner decision 2026-10-27; display only). Flagged lines (`unavailable`, `insufficient_stock`, `amount_out_of_range`) are listed but excluded from `merchandise_subtotal` and `item_count`. Totals come from `pricing.quote_merchandise`; requests carrying any price or total field get 422, and adding or updating a line into a total above the largest storable amount gets 422.

Browsers may send `X-Cart-Token` cross-origin from `CORS_ORIGINS` (`*` is refused). Limits:
- **New guest carts:** 10 per client network (IPv4 address, including IPv4-mapped IPv6, or IPv6 /64) per hour (ADR-008 S1, approved 2026-10-24). Beyond it, 429 `rate_limited` with `Retry-After`; while Redis is down, 503 `cart_creation_unavailable`, and existing carts keep working.
- **Repeated 409 `insufficient_stock`:** 20 per 15 minutes per network and per owner (ADR-008 S3, direction approved; details pending). Beyond it, further adds and quantity increases get 429. The limit is skipped, with a warning, while Redis is down.
- **Never limited:** lowering, removing and reading.

A successful merge writes one `cart.merge` audit record (IDs and counts plus the actor snapshot common to all audit records, never a credential; ADR-008 S4).

## Delivery and settings

Module 12 (TC-17; plan §5; RE-026 B1, B5, B6). One zone per supported district (Gasabo, Kicukiro, Nyarugenge), with one flat, VAT-inclusive fee. Delivery is free when the merchandise subtotal after discount is at least the `delivery.free_delivery_threshold` setting (199 999 pays the fee and 200 000 is free at a 200 000 threshold). A missing fee or threshold is never replaced by a default: quotes are refused instead. Changing a fee closes the current fee rule and adds a new one in one transaction, so the history is kept; at most one rule per zone is active (partial unique index). Zone code and district cannot be changed after creation. Staff changes are audited (`delivery.zone_create`, `delivery.zone_update`, `settings.update`); a request that changes nothing is not audited. Seed values are development placeholders (`scripts/seed_dev.py`).

## Inventory

Stock figures for staff (ADR-002 stock lifecycle; module 10 list). `inventory:read`: administrator, sales, operations, management; `inventory:adjust`: administrator, sales, operations (final matrix, 2026-10-26). Finance and customers get 403 `permission_denied`; no token gives 401.

- Figures, one calculation for the list and the single-SKU read (`app.services.inventory.stock_figures`):
  - `reserved_quantity` counts units in `active` reservations and `committed_quantity` units in `committed` ones; released, expired and fulfilled reservations hold nothing;

- Low stock: `available_quantity <= low_stock_threshold` and `low_stock_threshold > 0` (`is_low_stock`). The low-stock alert is `GET /api/v1/inventory?low_stock=true` (§7 Q9).

## Staff reports

- Sales count only paid orders and delivered cash-on-delivery orders: the orders with a `succeeded` payment attempt (mobile money through its verified webhook; cash on delivery only on delivery, §7 Q14). ## Endpoint coverage and requirements gaps

Implemented API search/filter/sort/pagination is limited to the public product listing. Staff listing and audit-log listing also have their own filters and pagination; neither is a commerce listing. No route implements:

- real MTN MoMo, Airtel Money or card payments (only the mock and cash on delivery exist until ADR-003, §7 Q21);
- EBM (RRA electronic billing) integration: invoices are issued by this API (module 16) without any EBM claim (PR-14);
- automatic re-issuance of refused invoices: an administrator recovers each one (`POST /api/v1/staff/orders/{order_id}/invoice`).
- invoices for orders paid before module 16 is deployed: none exist, and retroactive issuance waits for a Finance decision (no policy is assumed).
- real SMS delivery, or production email delivery: order notifications and password-reset codes use the mock, the development console or, for development and staging tests, SMTP email (for example Gmail) until ADR-005 chooses a provider (§7 Q22), plus temporary Gmail on the Render test deployment (`TEMPORARY_GMAIL_SMTP_ENABLED`) until Resend replaces it; provider delivery reports are not received, so `sent` means the SMTP server accepted the message, not that it reached the inbox;
- notifications for orders changed before module 17 is deployed, and for the `received` and `processing` statuses (not notified events).
- report definitions that are engineering defaults, not approved: the sale date, the top-products ranking and limit, the 366-day range limit and the presentation of empty periods (module 18, R-1 to R-4); the exported columns, which need the product owner's sign-off as the approved data for export (R-7); and whether exports should be audited, an open policy choice for the security owner (R-6). Refunds and returns, which no module records yet, are not subtracted.

Delivery fees and the cart delivery quote are implemented (module 12, above). Discount, tax and order-total pricing at checkout (RE-026) come with modules 13 and 14; see the [RE-026 blocker register](../architecture/RE-026-pricing-blockers-and-readiness.md).

The repository contains commerce models, inventory/order service functions and an internal merchandise-pricing service (RE-026 S1, `app/services/pricing.py`), but their existence is not an HTTP API. In particular, do not infer that checkout or order totals are available to clients. The product and project requirements come from the Product Requirements Document (PRD), Technical Delivery and Implementation Plan, and QA/UAT Checklist linked from `docs/requirements/README.md`; the board's current task cards and ordering remain unverified.

Relevant source acceptance criteria include PR-02 and PR-04 (catalogue browse/filter/sort/search), PR-05 (cart and checkout), PR-06 (account and order history), PR-07 (order statuses), PR-08 (payments), PR-09 (stock), PR-10 (admin catalogue), PR-11 (delivery fees), PR-12 (discounts), and QA scenarios TC-02 through TC-19. Current code provides API support for parts of PR-02/PR-04 and portions of the account/staff requirements. Order fulfilment status updates and assignment are available, but order creation, complete customer order history, delivery pricing, payment, and the broader purchase journey are not implemented through this API. This inventory does not mark requirements or Trello tasks complete.
