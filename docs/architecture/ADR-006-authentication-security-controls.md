# ADR-006: Authentication security controls (rate limiting, audit integrity, address defaults)

Status: **Accepted (project owner, 2026-10-21; staff decisions added 2026-10-22)** for the decisions marked *Approved*. Items under "Still open" remain unapproved and are not implemented.

Context: the 2026-10-21 acceptance audit (`docs/qa/acceptance-audit-auth-accounts-2026-10-21.md`) blocked approval of the authentication/accounts card. ADR-001 and RE-004 list authentication/session/roles as unresolved. This ADR records the decisions taken to correct the audit defects without replacing the existing architecture: opaque bearer tokens stored as SHA-256 hashes in PostgreSQL, scrypt passwords, and FastAPI dependencies for authorization.

| Password reset (project owner, 2026-10-23; implementation plan Q1/Q2) | **Customers only**: staff, inactive and unknown accounts get the same 202 reply but no code (staff passwords stay administrator-managed). `POST /auth/forgot-password` sends a 6-digit code to the given email or phone (email or SMS), valid 15 minutes and 5 attempts; a new request supersedes older codes. ## Engineering decisions (within existing approvals)

- **Atomic audit.** Repositories only flush. Each service commits the business change and its audit record in one transaction (`app/db/transaction.atomic`), so a failed audit write rolls the change back. Failure-only security events (failed login, access denied) are committed on their own.
- **Bounded metadata.** User-Agent is stripped of control characters and truncated to 512. IPs are validated with `ipaddress`. Audit `details` are size-, depth- and length-bounded. Secrets are redacted, and raw identifier keys are replaced.
- **Invalid-session audit throttling (2026-10-23, QA D-11).** A bearer token that matches no session returns 401 and writes no audit row, so anonymous callers cannot grow the append-only table. A token of an expired or revoked session writes `auth.session_invalid` (entity `session`, the session ID; reason `session_expired` or `session_revoked`) at most once per session per 15 minutes, enforced with a per-session advisory lock (namespace 7303). Probing with random tokens is no longer audited; tokens are 256-bit random values, so guessing is not a realistic attack.
- **Redacted application logs (2026-10-23, module 1).** `app/core/logging.py` installs one stderr handler (level from `LOG_LEVEL`) on the root and uvicorn loggers. Its formatter redacts the final text of every line, tracebacks included: Bearer tokens, secret-named key/value pairs (password, token, secret, authorization, API keys, reset codes), credentials in connection URLs, email addresses and Rwandan phone numbers. Code still never logs request bodies; the error handler logs only method and path.
- **Append-only audit at DB level.** A trigger blocks UPDATE/DELETE/TRUNCATE on `audit_records` for every role, including the owner. The only exception is the `users` foreign key `ON DELETE SET NULL` clearing `actor_user_id`.
- **Runtime vs migration roles.** `DATABASE_URL` uses the least-privilege runtime role `rwanda_app`, provisioned by `scripts/provision_runtime_role.py` with an explicit allow-list:
  - `users` / `user_sessions`: SELECT, INSERT, UPDATE
  - `password_reset_codes`: SELECT, INSERT, UPDATE (password reset: codes are issued, their attempts counted, then marked used or superseded; never deleted)
  - `addresses`: SELECT, INSERT, UPDATE, DELETE
  - `staff_role_assignments`: SELECT, INSERT, UPDATE (staff provisioning and role changes; no DELETE)
  - `audit_records`: SELECT, INSERT
  - `alembic_version`: SELECT
  - `categories` / `brands` / `products` / `product_variants` / `product_images`: SELECT (public catalogue; added 2026-10-22, when it was found returning 500 on this role)
  - `categories` / `brands`: also INSERT, UPDATE, DELETE (module 5 staff management, 2026-10-23). DELETE removes only unused rows; the service refuses referenced ones and the RESTRICT foreign keys remain the final guard. These and `addresses` were the only tables with DELETE until module 7 added `product_images`.
  - `products` / `product_variants`: also INSERT, UPDATE (module 6 staff management, 2026-10-23). No DELETE: a variant DELETE deactivates the row.
  - `product_images`: also INSERT, UPDATE, DELETE (module 7 staff image management, 2026-10-24). An image DELETE removes the row and then its files; no table references `product_images`. It joins `addresses`, `categories` and `brands` as the only tables with DELETE.
  - `import_jobs`: SELECT, INSERT, UPDATE (module 8 catalogue import, 2026-10-24). A job is inserted as `processing` and finished in place; jobs are never deleted. The import writes products, variants and opening-stock receipts through the existing grants on those tables.
  - `carts`: SELECT, INSERT, UPDATE; `cart_items`: SELECT, INSERT, UPDATE, DELETE (module 11 cart, 2026-10-24). Carts are created and then updated (expiry, `converted` after a merge, `abandoned` once expired); they are never deleted. Cart lines are removed by `DELETE /cart/items/{id}`, which makes `cart_items` the fifth table with DELETE.
  - `discounts`, `discount_redemptions`: SELECT, INSERT, UPDATE; `discount_targets`: SELECT, INSERT, DELETE (module 13 promotions, 2026-10-25). Codes are created and edited and row-locked at checkout; redemptions are inserted at checkout and released in place; neither is deleted. Targets are replaced as a set, which makes `discount_targets` the sixth table with DELETE.
  - `delivery_zones`, `delivery_fee_rules`, `settings`: SELECT, INSERT, UPDATE (module 12 delivery, 2026-10-24). Zones are created and edited; a fee change closes the active rule in place and inserts its replacement, so fee rules are never deleted and the history is kept; settings are upserted by administrators. No DELETE on any of them.
  - `orders`: SELECT, INSERT, UPDATE; `order_items`: SELECT, INSERT; `order_status_history`: SELECT, INSERT (order fulfilment, 2026-10-23; checkout, module 14, 2026-10-25). Checkout inserts the order and its line snapshots; fulfilment and the expiry job update the order's status and assignee (UPDATE also covers SELECT ... FOR UPDATE); each status change adds one history row. Order lines are never changed after checkout. None of these is deleted.
  - `payment_attempts`: SELECT, INSERT, UPDATE (module 14, 2026-10-25). Checkout records the chosen method as the first attempt; its status changes only as §7 Q12–Q14 allow (`cancelled` on cancellation, `expired` with the hold, `succeeded` for cash on delivery on delivery). Never deleted.
  - `inventory_balances`: SELECT, INSERT, UPDATE; `stock_movements`: SELECT, INSERT (staff stock adjustments create the balance on first receipt; the ledger is append-only; dispatch adds its movements)
  - `stock_reservations`: SELECT, INSERT, UPDATE (module 14 checkout inserts the holds; availability reads; the expiry job, cancellation, commit and dispatch change their status). No DELETE; a database trigger keeps a hold immutable apart from its status and, while it is active, its expiry, capped at 24 hours after the hold was created (payment-method switch, migration `a8d2f6c1e3b7`, 2026-10-27).
  - `payment_events`: SELECT, INSERT, UPDATE (module 15 payments, 2026-10-25). A verified webhook is inserted once per (provider, event key) and then marked processed or needs-reconciliation in place; sanitised metadata only. Never deleted. `payment_attempts` (above) also gains attempts from payment initiation.
  - `notification_logs`: SELECT, INSERT, UPDATE (module 17 notifications, 2026-10-26). Inserted in the order's transaction, then claimed (`FOR UPDATE SKIP LOCKED`) and updated per attempt by the API and `scripts/retry_notifications.py`; recipients are stored, message text is not; never deleted.
  - **Not granted:** DELETE on every order, payment, reservation, ledger, promotion code and redemption table. Any future privilege is added to `TABLE_GRANTS` in the change that needs it, pinned in `tests/unit/test_runtime_role_grants.py` and recorded here.

  The role is not owner or superuser and has no CREATE on the schema.
- **Staff change serialisation.** Staff creation and every role, status or detail change take a transaction-scoped PostgreSQL advisory lock, then re-read the acting administrator. A concurrently demoted or disabled administrator therefore cannot finish a change, and two administrators demoting each other always leave one active administrator.
- **Staff administration scope.** Staff endpoints return 404 for customer IDs; customers are never converted to staff. Editable staff details are `full_name` and `phone` (as in the customer profile); email, password, role, status and flags are rejected with 422 there. Setting the current role or status is a no-op (no audit, sessions kept). Every change is audited (`staff.create`, `staff.update`, `staff.role_change` with old/new role, `staff.status_change`, `staff.bootstrap_administrator`) in the same transaction.
- **No echo of submitted values.** 422 responses carry only `type`, `loc` and `msg`; FastAPI's default `input` field was removed because it echoed submitted passwords. Alembic uses `MIGRATION_DATABASE_URL` (the schema owner); an empty value falls back to `DATABASE_URL`.

- **Bootstrap hardening (2026-10-22, security fix).** `bootstrap_admin.py` connects only with `MIGRATION_DATABASE_URL` (the owner account). It refuses if that is unset or is the application account; there is no fallback to `DATABASE_URL`. The `staff.bootstrap_administrator` audit record now also stores `mode` (`first` or `recovery`), `db_role` (the database account used) and `os_user`. Concurrent runs are serialised by the staff-change lock, which a test covers.
- **No fixed test credentials; isolated smoke checks (2026-10-22, security fix).** Earlier versions of `scripts/verify_postgres_live.py` contained fixed staff passwords, including an administrator's, and created those accounts. The passwords remain in Git history (commits `bfb7063`, `cd4015b`), so they must be treated as public. The script now:
  - runs only against `SMOKE_DATABASE_URL`, never the `.env` database settings;
  - refuses unless the database name ends in `_test`, the host is loopback, `APP_ENV=development`, `SMOKE_CONFIRM_DISPOSABLE` repeats the database name, the target is not the `.env` database, and no staff account exists outside the reserved test domains (`.invalid`, `.test`, `@example.com`);
  - creates run-scoped accounts (`smoke.<run>.*@smoke.invalid`) with random passwords and a random audit HMAC key, none of which are printed or stored;
  - deletes only those accounts afterwards and keeps their audit records.

  Pytest staff fixtures and the PostgreSQL suite also generate passwords per run (`tests/support/credentials.py`).

## Rebase onto the commerce identity schema (2026-10-21)

PR #2 (`8f534feaaedc` → `f6ee0bc51c3c`) introduced the shared `users`, `addresses`, `staff_role_assignments` and `audit_records` tables. Approved by the project owner (option A): authentication now builds on that schema instead of its own tables.
- The former auth migrations `87668c54003d` and `5c2f9a1d7e40` were removed. A single follow-up revision **`9b3e5d2a1c07`** (after `f6ee0bc51c3c`) adds `user_sessions`, `users.full_name` (nullable), canonical-phone CHECKs on `users.phone`/`addresses.phone`, and the append-only audit trigger.
- **Roles:** staff roles come from `staff_role_assignments` (`administrator`, `sales`, `operations`, `management`, `finance` since 2026-10-25) and count only when `users.is_staff` is true; everyone else is `customer`. Public registration sets `is_staff=false` and creates no assignments.
- **Audit mapping:**
  - `actor_user_id`, plus `actor_identifier_snapshot` (the actor's email, else phone)
  - `action`
  - `entity_type`/`entity_id`: the affected record; failed logins use `login_identifier` + HMAC pseudonym
  - `change_summary` JSONB: `status`, `ip_address`, `user_agent` and bounded details
- **API field names follow the schema:** `phone` (not `phone_number`). Address responses add the upstream `label`, `province`, `village` and `country_code` (`RW`).
- Database tests now run only on PostgreSQL (per-test schema migrated by Alembic, as in the commerce tests). The schema uses JSONB, regex CHECKs and triggers, which SQLite cannot represent.
- **One identifier policy.** `app/core/identifiers.py` normalises email (lower-case, ≤254 chars) and Rwandan mobile numbers (`+2507XXXXXXXX`, `2507XXXXXXXX`, `07XXXXXXXX` → `+2507XXXXXXXX`) for registration, login, profile and addresses. A PostgreSQL CHECK keeps stored phones canonical.
- **Uniqueness races.** `IntegrityError` on unique email/phone is mapped to 409 without exposing database details.
- **Anti-enumeration timing.** Unknown-account logins perform the same scrypt work as real ones.

## Amendment: Continue with Google (2026-11-11, backend only; pending owner review)

Requested by the project owner on 2026-11-11 ("Continue with Google", backend first). Implemented in the backend and tested; the storefront part is not built and waits for the owner's review.

- **Protocol.** OAuth 2.0 Authorization Code flow with PKCE (S256) and OpenID Connect. Scopes `openid email profile`, `prompt=select_account`, no offline access. Google's access token is never used or stored; only the ID token's identity is.
- **One session system.** A Google sign-in issues the same database session as password login (opaque bearer token, SHA-256 stored, 7 days, revocable; `POST /auth/logout`, `logout-all`, deactivation and password reset apply unchanged). The storefront keeps it in the `sixty_session` httpOnly cookie as before.
- **Endpoints.** `POST /auth/google/start` and `POST /auth/google/callback` (sign-in); `POST /auth/google/link/start` and `POST /auth/google/link/callback` (a signed-in customer links Google). See docs/api/endpoint-inventory.md.
- **Flow state** (`oauth_login_flows`). Per start: `state`, `nonce`, a PKCE verifier and a browser-binding `flow_token`, all from `secrets` (≥256 bits). Only SHA-256 digests of the state, flow token and nonce are stored; the verifier is erased when the flow is used. Flows expire after `GOOGLE_OAUTH_FLOW_TTL_SECONDS` (default 600) and are deleted a day after expiry.
- **CSRF and replay.** The storefront must keep the `flow_token` in a short-lived httpOnly, `SameSite=Lax` cookie and send it with the callback. A flow is consumed by one locked `SELECT … FOR UPDATE` + `UPDATE` that requires the matching state **and** flow token, unused and unexpired, committed before Google is called. A replayed, expired, forged (login CSRF: someone else's state and code) or other-browser callback gets 422 `google_state_invalid` (like a wrong reset code) without a call to Google; a wrong flow token does not use up the rightful browser's flow.
- **ID token checks.** RS256 only, against Google's JWKS (cached for Google's max-age, at most a day; an unknown key ID refreshes at most once a minute, counting failed attempts; after a failed fetch of expired keys requests get 503 for 10 s instead of each retrying); issuer `https://accounts.google.com` or `accounts.google.com`; audience = our client ID; `azp`, when present, = our client ID, and required when there are several audiences; `exp`/`iat` with 60 s skew; nonce = the flow's (compared by digest, constant time); `sub` required. `email_verified` must be true, and the email must pass the registration rules (`validate_email_format`). The display name is cleaned (printable characters, single spaces, 2-255 characters, else the email's local part) and only shown.
- **Account linking rules.**
  1. Accounts are matched by Google's subject (`oauth_identities`, unique per (provider, subject) and per (user, provider)), never by email.
  2. A new Google account whose email no account uses creates a **customer** (`is_staff=false`, no role, no password). Nothing from Google (claims such as `hd`, extra fields) can grant a role.
  3. An email already used by any account is refused with 409 `google_account_exists`: the owner signs in with the password and links Google from the profile. Automatic linking by email was rejected because accounts here are not email-verified: someone who registered another person's address could otherwise have that person's Google sign-in joined to an account they control (pre-account takeover). Staff and customer emails get the same answer.
  4. Staff never sign in or link with Google (403 `google_staff_not_allowed`); their accounts stay administrator-provisioned with passwords.
  5. Concurrent first sign-ins are settled by the unique constraints: the losing request is answered as if it had arrived second (signs in, or 409).
- **Errors** (standard error body; the API documents no 400s, so refused callbacks are 422 like `reset_code_invalid`): 422 `google_state_invalid`, `google_auth_cancelled` (user cancelled at Google), `google_auth_failed`; 401 `google_code_invalid`, `google_token_invalid`; 403 `google_email_unverified`, `google_email_invalid` (outside the shop's email rules), `google_staff_not_allowed`, `account_inactive`; 409 `google_account_exists`, `google_already_linked`, `google_account_in_use`; 429 `rate_limited`; 503 `google_auth_unavailable` (not configured), `google_unavailable` (Google unreachable, 5xx, timeout, or our client refused), `login_unavailable` (rate-limit store down; fail closed).
- **Abuse limits.** Every start and failed callback counts per client network (IPv4 address or IPv6 /64): `GOOGLE_AUTH_MAX_PER_NETWORK` (30) per `GOOGLE_AUTH_WINDOW_SECONDS` (900), in Redis like the login limits.
- **Secrets and logging.** `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` (SecretStr) and `GOOGLE_OAUTH_REDIRECT_URI` come from the environment, all three or none; the redirect URI must be https:// outside development. Codes, tokens, the verifier, the state, the flow token and the client secret are never logged or audited; Google's error responses are reduced to a short error code. Audit: `auth.register` / `auth.login` with `provider: google`, `auth.google_link`, and `auth.google` failures with a reason (Google subjects and emails as keyed pseudonyms).
- **Dependencies.** `pyjwt[crypto]` (RS256 verification through `cryptography`) and `httpx` (calls to Google; it was already a development dependency) became runtime dependencies.
- **Database.** Migration `d5a9c3e7f2b8` (after `a9d3f7c2e5b8`, category spotlight product) adds `oauth_identities` and `oauth_login_flows`; the runtime role gets SELECT/INSERT/UPDATE on identities and SELECT/INSERT/UPDATE/DELETE on flows (`scripts/provision_runtime_role.py`). The downgrade refuses while any Google identity exists.
- **Storefront (2026-11-12).** The Next.js app is the only caller, through its route handlers (`frontend/src/lib/google-auth-handlers.ts`):
  - `POST /api/auth/google/start` and `/api/auth/google/link/start` (same-origin only; link needs the session cookie) call the backend and keep the `flow_token` in the httpOnly cookie `sixty_google_flow` (SameSite=Lax, so it survives Google's top-level redirect back; Secure in production; path `/api/auth/google`; it expires with the flow, at most 30 minutes). The cookie also holds the purpose, the page it started from, a `safeReturnTo` path, the language and a hearted product's UUID, each validated again when read. The page receives only `authorization_url`, accepted only when it is `https://accounts.google.com/…`.
  - `GET /api/auth/google/callback` (the backend's `GOOGLE_OAUTH_REDIRECT_URI`) always clears that cookie, refuses a missing or invalid flow without calling the backend, forwards exactly `{state, flow_token, code | error}` to `/callback` or `/link/callback` by the stored purpose, and on sign-in sets `sixty_session` and merges the guest cart exactly as password login does. It answers with a 303 (`Cache-Control: no-store`, `Referrer-Policy: no-referrer`) to a clean page URL; errors reach the page only as a code from a fixed list (`?google_error=`), never the backend's message.
  - The general proxy (`/api/backend/*`) refuses every `api/v1/auth/google/*` path (decoded and lower-cased) and strips any `flow_token` from responses.
  - `GET /auth/me` adds `google_linked` and `has_password` for the profile's Connected accounts; a Google-only customer sees "Set a password" (the reset-code flow) instead of the change-password form.
- **Not built yet (open).** Unlinking Google; a customer created by Google has no password until they set one through the reset code.

## Amendment: email verification of new customer accounts (2026-11-12, backend only; pending owner review)

Requested and approved by the project owner on 2026-11-12, with these choices: phone-only registration is unaffected; registration with an email answers 503 when no email can be delivered; the welcome email follows verification; password reset stays separate. Contract and frontend requirements: `docs/api/email-verification.md`.

- **Who must verify.** A customer who registers with an email address (and a password) is created unverified (`users.email_verified_at` NULL) and gets **no session** until the address is verified. Password login refuses them with 403 `email_not_verified`, checked only after the password is correct, so the answer reveals nothing to someone without it; it does not count as a failed attempt. Phone-only accounts have no email and are unaffected. Staff are never asked to verify. Migration `e6b1d4a8c2f7` marks every existing account with an email verified at its creation time, so nobody is locked out. Customers created by Continue with Google are verified at creation (the ID token's `email_verified` claim is already required); Google never links to an unverified password account (409 `google_account_exists`, unchanged), and such an account cannot sign in to link it.
- **Tokens.** 256 random bits (`secrets.token_urlsafe(32)`); only the SHA-256 digest is stored (unique), with the address it verifies, `expires_at` (`EMAIL_VERIFICATION_TTL_HOURS`, 24) and `consumed_at` / `revoked_at` (never both). A new link revokes older open ones; verifying revokes the account's other open links. The link is `SITE_URL/verify-email#token=…`: the fragment never reaches servers or Referer headers.
- **Verify.** `POST /auth/email/verify` locks the token row (`SELECT … FOR UPDATE`), checks it (known, not revoked, not used, not expired, still the account's address), consumes it and marks the account verified in one transaction with its audit record; a concurrent use waits for the lock and then finds it used (tested with a proven overlap). Failed attempts count per client network (30 per 15 minutes). It does not sign in.
- **Resend.** `POST /auth/email/verification/resend` gives the same 202 for an unverified customer, a verified one, staff, an inactive account, an unknown address or a cooldown (60 s). Every request counts against 5 per address and 20 per IP per hour (429), so the limit reveals nothing either.
- **Delivery.** Through the existing notification provider abstraction (`get_message_sender`: a provider that reaches people) and `SITE_URL`, wrapped as `VerificationMailer` (`app/integrations/notifications/verification.py`; tests override it with a recording sender). Without either, registration with an email and resend answer 503 `email_verification_unavailable` before anything is created or looked up. The link is sent once after the commit, never stored in `notification_logs`, logs or audit; a failed delivery is logged by error type only and leaves the account unverified (resend). The welcome email is recorded when the address is verified.
- **Database.** `users.email_verified_at`, table `email_verification_tokens`; the runtime role gets SELECT/INSERT/UPDATE on it. The downgrade stops while any customer with an email is unverified (older code would let them sign in).
- **Not built (open).** The storefront `/verify-email` page and the "check your email" / resend screens; phone ownership verification; changing an email address (no such endpoint exists); clean-up of never-verified accounts and of old token rows.

## Amendment: the client IP behind the storefront (2026-11-13; approved by the project owner)

Shoppers reach the API through the storefront's server (the Next.js backend-for-frontend on Vercel) and the API host's load balancer (Render), so the API's transport peer is never the shopper. Using it would put every customer in one per-IP rate-limit bucket; trusting `X-Forwarded-For` would let any caller of the public API choose its own address (uvicorn's `--forwarded-allow-ips="*"` takes the leftmost, caller-written entry). Neither is acceptable. Render documents no client-IP forwarding and its proxy addresses are not published, so the design depends on neither.

- **Signed client IP.** With `CLIENT_IP_SOURCE=vercel` (frontend), the storefront's server reads the shopper's address only from the headers Vercel's edge sets (`x-vercel-forwarded-for`, then `x-real-ip`; Vercel overwrites client-supplied values to prevent spoofing) and adds to every API call `X-Sixty-Client-IP`, `X-Sixty-Client-IP-Timestamp` (Unix seconds) and `X-Sixty-Client-IP-Signature`: hex HMAC-SHA256 with `CLIENT_IP_SIGNING_SECRET` over `sixty-client-ip-v1\n<timestamp>\n<ip>\n<METHOD>\n<path>`. It never passes on the browser's `X-Forwarded-For`, and only these generated `X-Sixty-*` headers reach the API (the general proxy copies an allowlist of headers). Without `CLIENT_IP_SOURCE` (local development) it adds nothing (`frontend/src/lib/client-ip.ts`).
- **Verification.** With `CLIENT_IP_SOURCE=signed` (backend), `app/core/request_context.py` accepts the address only when each header appears once within its size limit (45, 12 and 64 characters), the timestamp is within `CLIENT_IP_SIGNATURE_MAX_AGE_SECONDS` (60) of the API's clock in either direction, the signature matches `CLIENT_IP_SIGNING_SECRET` or `CLIENT_IP_SIGNING_SECRET_NEXT` (compared in constant time) for this request's method and path, and the value is one valid IPv4 or IPv6 address. Anything else (missing, malformed, oversized, repeated, stale, wrong signature, another endpoint) falls back to the transport peer, so a caller can neither choose an address nor escape a limit by inventing one. A refusal is logged with its reason only. `X-Forwarded-For` is never read; uvicorn runs with `--no-proxy-headers`.
- **Rotation.** The API accepts the current and the next secret: set `CLIENT_IP_SIGNING_SECRET_NEXT` on the API, switch the storefront to the new secret, then make it the API's current secret and clear the next one. Preview and Production use different secrets.
- **Fail closed.** `CLIENT_IP_SOURCE=signed` without a secret of at least 32 characters, a next secret equal to the current one or too short, or signing secrets without `CLIENT_IP_SOURCE=signed`, stop the API at startup in every environment; `CLIENT_IP_SOURCE=vercel` without a usable `CLIENT_IP_SIGNING_SECRET` stops `next build` and `next start`. With `APP_ENV=production` and `CLIENT_IP_SOURCE=peer` the API logs a warning at startup. Secrets are `SecretStr` and never logged; `signature` is a redacted key in the log filter.
- **Residual risks.** A leaked signing secret lets its holder claim any address for rate limits and audit records until it is rotated (authentication is not affected). A captured set of headers can be replayed only against the same method and path within the freshness window. Calls from the storefront's server that are not made for a shopper (catalogue pages) carry no address and use the transport peer; none of them is rate-limited per IP.

### Client IP addresses: purpose, access and retention

| Where | Purpose | Who can read it | Retention |
| --- | --- | --- | --- |
| Redis rate-limit counters | Abuse prevention (per-IP and per-network limits) | The API only | Expire with their window (at most 1 hour); automatic |
| `user_sessions.ip_address` | Account security: where a session was created | Database operators | Policy: 30 days after the session expired or was revoked |
| `audit_records.change_summary.ip_address` | Security investigation and accountability | Staff with `audit:read` (finance, administrator) and database operators | Policy: 12 months, then the address is removed (the record stays) |

The 30-day and 12-month periods are the adopted policy; **enforcing them is not built yet**. A scheduled clean-up of sessions and of addresses in audit records changes stored records (audit records are otherwise append-only), so it needs its own approval and implementation before launch. Until then addresses are kept, and this is tracked under "Still open".
