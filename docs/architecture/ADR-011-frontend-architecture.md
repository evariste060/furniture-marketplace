# ADR-011: Frontend architecture (Next.js 16)

Status: **Accepted** by the project owner on 2026-10-26 (frontend phase 1, step 2 decisions). Scope: the `frontend/` app.

## Decisions

1. **One Next.js app** (App Router, Next.js 16, Cache Components on) for the storefront and the admin. Three root layouts: `app/[locale]` (storefront), `app/admin` (English or Kinyarwanda, see "Admin language" below) and `app/dev` (the development component gallery at `/dev/ui`, absent from production builds unless `ENABLE_DEV_UI=true` is set at build time).
2. **API types are generated** from the backend OpenAPI with `openapi-typescript` (`npm run api:types` → `src/lib/api/schema.d.ts`, committed). One typed client: `openapi-fetch`. Response types are never written by hand.
3. **Server Components call the backend directly** at `API_URL` (`src/lib/api/server.ts`). Public catalogue data (categories, products, banners) is cached with `"use cache"` and the `catalogue` cache profile (`next.config.ts`: stale 30 s, revalidate 60 s, expire 120 s). The short expiry keeps it out of the build-time prerender, so `next build` never needs the backend. Cart, account and admin data are never cached.
4. **The browser never calls the backend.** Client code (TanStack Query) calls one route handler, `/api/backend/[...path]` (`src/lib/backend-proxy.ts`):
   - it forwards only `/api/v1/...` paths, and refuses sign-in, registration and sign-out (they have their own handlers);
   - it adds `Authorization: Bearer` and `X-Cart-Token` from httpOnly cookies, and ignores any credentials the page sends;
   - it refuses mutating requests whose `Origin` is not this site (`SITE_URL`, or the request's own origin in development);
   - a guest cart token returned by the backend is moved into the cart cookie and removed from the body; a 401 clears the session cookie;
   - it forwards `X-Forwarded-For` so the backend's per-network limits still see the client. The backend must trust this app's address in `FORWARDED_ALLOW_IPS` (deployment note).
5. **Cookies** (ADR-006, frontend token storage): `sixty_session` and `sixty_cart`, httpOnly, `SameSite=Lax`, `Secure` in production, path `/`. The session cookie expires with the backend session; the cart cookie after 30 days (the backend's guest cart expiry). `/api/auth/login` and `/api/auth/register` set the session cookie and merge the guest cart (`POST /cart/merge`, best effort) and clear the cart cookie; `/api/auth/logout` revokes the session at the backend and clears the cookie.
6. **Admin access** is checked on the server for every admin page (`src/lib/staff.ts`: `/staff/me` and `/staff/me/permissions`). The sidebar hides what a role lacks and a direct URL shows AccessDenied. The backend enforces every permission again.
7. **i18n**: `next-intl` with `next/root-params`. English at `/`, Kinyarwanda under `/rw` (`localePrefix: "as-needed"`, no detection from the browser). All storefront copy is in `messages/en.json` and `messages/rw.json`; the Kinyarwanda is a draft until a native speaker approves `docs/frontend/rw-review.md` (generated by `npm run i18n:review`, checked by a test). Banner text comes from the API in `{en, rw}`. The admin's copy is in `messages/admin.json` and `messages/admin.rw.json` (draft Kinyarwanda in `docs/frontend/rw-review-admin.md`).
8. **Images** (ADR-009): `next/image` with `deviceSizes` 400/800/1600 and `imageSizes` 64/128/256; allowed hosts from `IMAGE_REMOTE_PATTERNS`. The optimizer may fetch from a local IP only when a configured host is local (development). All image URL logic is in `src/lib/images.ts`, where the Cloudflare loader is added later. A missing or broken image shows a grey box with the package icon (`ProductImage`).
9. **Design tokens** from `frontend/design/tokens-and-components.css` are the Tailwind theme (`src/app/globals.css`); the default Tailwind palette is removed so only token colours exist. Inter is self-hosted with `next/font/local` (`src/app/fonts/InterVariable.woff2`, rsms/inter v4.1, SIL OFL 1.1 in `src/app/fonts/LICENSE.txt`; decided 2026-10-27), so neither the build nor the browser contacts Google Fonts. Icons from `lucide-react`.
10. **Quality**: ESLint with `typescript-eslint`, React Hooks and `eslint-plugin-jsx-a11y-x` (the maintained fork of `eslint-plugin-jsx-a11y`, now under the `eslint-community` GitHub organisation; the original does not support ESLint 10), pinned to an exact version, strict rules. Kept on 2026-10-27 because it met the owner's bar (at least 10k weekly downloads and a release in the last 6 months): 177,356 downloads in the week of 19–25 Oct 2026, release 0.2.0 on 2026-05-10, npm maintainer `43081j`. If it falls below that bar, move to ESLint 9 with `eslint-plugin-jsx-a11y`; Vitest with Testing Library; Playwright against a production build with an axe (WCAG 2.1 A/AA) check on every page and screenshots at 1440 px and 390 px.

## Deviations from the design, for the owner

- **Contrast (WCAG AA)**: three token pairings in the design are below 4.5:1, so existing darker tokens are used instead: blue text on light blue (`--pri` on `--light`, 4.44:1) uses `--pri-h` (6.15:1) for the secondary button, the soft "info" badge and the hero overline; solid green badges (white on `--ok`, 3.30:1) use `--ok-tx` (5.02:1); table header text (`--mut` on `--page`, 4.47:1) uses `--tx2` (7.11:1).
- **Toast**: not drawn; built from the Contact.dc.html success banner.
- **Overlays** (decided 2026-10-27): dialogs (forms, confirmations) close with Escape or the close button only, so no data is lost by a stray click; drawers (mini cart, filters, mobile menu) also close on a click outside. Both trap focus while open and return it to the control that opened them.
- **Toast** and **contrast** substitutions approved by the owner on 2026-10-27.

## Frontend phase 2 (2026-10-27)

- **Per-visitor parts load in the browser.** The cart count, the wishlist hearts and count, and the account label come from TanStack Query (`/api/auth/session`, `GET /cart`, `GET /customers/me/wishlist/ids`), so the catalogue pages stay cacheable and identical for everyone. `/api/auth/session` answers a guest `{user: null}` without calling the backend and returns only the header's fields.
- **Listing state is in the URL** (`brand` repeated, `min_price`/`max_price`, `stock=in|out`, `rating`, `sort`, `view`, `page`; `src/lib/catalogue.ts`). Invalid values are dropped rather than sent to the API. The filter panel shows live counts from `GET /catalog/facets` for the options being chosen and applies them with "Apply Filters" (desktop) or "Show N products" (mobile sheet).
- **Cards' Add to Cart**: a product with one variant is added at once (toast with a link to the cart); one with several variants opens its product page to choose. Out of stock is a disabled button. The mini cart drawer comes with the cart (phase 4).
- **Wishlist heart**: a guest goes to `/login?returnTo=…&wishlist=<product id>`; the login page (phase 5) saves the product after sign-in. Staff accounts get a short notice instead (the API refuses them).
- **Store contact details** (phone, WhatsApp, emails, address, hours, social links) are not shown, and the WhatsApp button is not built, until the settings API (module 19) provides them (owner decision 2026-10-27).
- **Info page slugs** linked from the footer: `/pages/delivery-information`, `returns-and-refunds`, `warranty`, `about-us`, `terms-and-conditions`, `privacy-policy` (module 19 serves them).
- **Contrast**: section descriptions on `--page` and breadcrumb links on `--light` use `--tx2` instead of `--mut` (same substitution as the table headers).

## Frontend phase 3 (2026-10-27)

- **One listing model** for Deals, Category, Brand and Search: the URL also carries `category` (one choice) and, on `/search` only, `q` (trimmed, at most 160 characters, as the header box). With a search the default sort is "Best match" (the API's relevance order); it does not exist without one. A page's own filter wins over the URL (a category page ignores `?category=`, a brand page ignores `?brand=`).
- **Category facet**: `GET /catalog/facets` gained `categories` (counts per category in the menu's order, ignoring the category filter) for the brand page's Category group and the search chips. The endpoint is extended rather than counted in the browser.
- **Pages with a dynamic segment** (`/category/[slug]`, `/brand/[slug]`, `/product/[slug]`) know their URL only at request time, so the header parts that read it (language links, the active nav link, the mobile tab bar, the search box's text) render inside small Suspense boundaries: the build's shell shows them without the current-page state, and the real ones stream in with the page.
- **Product page**: the variant picker groups the variants' attributes that differ (colour, storage, …; otherwise the variant names) and shows each choice's price or "Out of stock". Quantity 1–99 (the cart's line limit). Buy Now adds to the cart and opens `/checkout` (phase 4). On phones the Add to Cart / Buy Now bar takes the tab bar's place. Reviews: the first three from the server, "Show more reviews" loads the next pages in the browser; text is shown as plain text with its line breaks.
- **Home hero showcase motion and background** (owner, 2026-11-18): the hero runs the full width of the screen (no side margins, no card), its content on the page's 1240px width. The orbit of the categories' best sellers keeps turning, every 3 seconds whatever the category holds (`TURN_MS`; it still pauses on hover and keyboard focus and keeps the rest of its time), but no circle is drawn behind it: the products turn directly over the background. The copy fades up into place in a short sequence (eyebrow, name, category link, price, buttons) with no overshoot. Beside the spotlight are four related products (or services), not six, in a straight grid of equal tiles (2×2 on phones and laptops, one row of four on tablets) under a small "More in …" bar; they come in together, fading and rising into place, and leave together. The background is the owner's electronics-store photo (`public/brand/hero-background.jpg`, a static brand graphic) across the full width, served by `next/image` (AVIF/WebP at the screen's width, never the 2752px original) and loaded first with a blurred preview. A light white wash covers only the copy's side (the left; the top on phones) so the copy reads and the store stays clearly visible behind the orbit and the products. With reduced motion nothing animates.
- **Product page layout** (owner, 2026-11-18): on tablets and desktops the specifications sit under the photos in the left column, so the space under the gallery beside the long right column is used. The former Specifications / Description / Delivery & Returns tabs under both columns are removed: the description is already beside the price and the delivery, warranty, payment and returns card already in the right column, so the tabs repeated them. Phones keep the Specifications and Description accordions (the description is hidden beside the price there). Customer reviews without any review is one full-width card instead of a narrow card with empty space beside it.
- **Search result pages** are `noindex`.
- **Unknown slugs** show the not-found page with `noindex`. The HTTP status is 200, not 404: the lookup runs inside a Suspense boundary after the page shell is sent (Next.js streaming). Making these routes block until the product is loaded would give a 404 status but lose the streamed shell; not done.

### Design differences (phase 3), for the owner

- Category hero: the tagline beside the image ("Latest Phones. Brighter Possibilities.") is not shown; the API has no such field. The image is the category image.
- Search toolbar: the Brand and Price dropdowns are in the Filters panel (with availability and rating); "In stock only" is a toggle. The sentence "In-stock items are shown first" is left out (results are in best-match order).
- Product: colours are text buttons, not swatches (the API has no colour values); the stock badge has no "14 left" (exact quantities are not public); the "1-year warranty" badge on the image is replaced by the product's warranty text in the info card; the WhatsApp buttons, the business-quote link and the store contact details wait for module 19 (decision of 2026-10-27).
- Product info card: delivery fees and the free-delivery threshold come from the delivery zones (no delivery-day estimates); payment lists MTN MoMo, Airtel Money and cash on delivery (card is not offered); returns say "Easy returns" and link to the policy page instead of "7-day … unopened" until that policy is published.
- Reviews: no sort menu, no filtering by star row, no photos and no staff replies (module 20 lists approved reviews newest first, text only). The tabs are Specifications, Description and Delivery & Returns; the reviews are the section below them (the rating link jumps there).
- Mobile product and category pages keep the store header instead of a back-arrow header.

## Frontend phase 4 (2026-10-27)

- **Cart and mini cart**: `/cart` and the drawer read the cart in the browser through the proxy; every amount comes from the backend. "Add to Cart" (cards and the product page) opens the mini cart inside the store layout; elsewhere it falls back to the toast. Lines the backend flags (no longer sold, not enough stock, amount too large) block checkout until removed or changed. Price changes show "Price updated: was …" and "Accept changes" (backend `price_at_add`, owner decision 2026-10-27). "Save for later" moves a customer's line to the wishlist; a guest signs in first.
- **Forgotten guest carts**: when the backend answers `404 cart_not_found` to a guest (the cart expired, or became an order), the proxy deletes the cart cookie, so the next request starts a new cart.
- **Checkout** (`/checkout`, its own route group and layout: the checkout header and a small footer, no store navigation) is one client page with the step in the URL (`?step=`). What is typed stays in the page's memory only; a reload goes back to the first incomplete step. The browser checks the fields for messages; the backend checks them again and prices the order from the cart. The contact person is the recipient: the order always carries the address inline (from a saved address or the new-address form), with the contact's name and phone. Placing an order sends an `Idempotency-Key` that is reused while the order body is unchanged (a retry returns the same order) and replaced when it changes.
- **Guest access to a placed order**: the order number and the phone typed at checkout are kept in `sessionStorage` (this tab only, at most five orders, never sent anywhere but the backend's order endpoints). The payment page sends the phone as the guest proof (`phone` in the body, `X-Order-Phone` for status); the confirmation page uses `POST /orders/lookup`. Without it (another tab or device) the page asks for the phone. A signed-in customer needs no phone: the confirmation page finds the order in their order history.
- **Payment page** (`/checkout/pay/[orderNumber]`): starts the mobile money request once (a reload does not resend it: the backend returns the request already started), reads the status every 3 seconds, and moves to the confirmation page when the provider's signed notice marks it paid. Failed or cancelled requests show "Try again" (a new request) and "Choose another payment method" (`POST /payments/{n}/method`). An order whose stock hold has ended shows the expired state. Cash on delivery goes straight to the confirmation page.
- **Development payments**: `scripts/mock_payment.py ORDER --succeed|--fail` settles a mock request; the Playwright tests send the same signed event with `PAYMENT_MOCK_WEBHOOK_SECRET` from the environment. Each full Playwright run starts about nine guest carts, close to the backend's limit of 10 per network per hour (`CART_GUEST_CREATIONS_PER_IP`); repeated local runs need that counter to expire, or a higher limit in the local `.env`.
- `INFO_PAGES` moved to `src/lib/info-pages.ts` so client components can link to the policies. The design's `.kv` (label and value row) and `.hr` (divider) are Tailwind utilities in `globals.css`.
- Contrast (approved substitutions): grey captions on the light-blue selected option and on `--page` use `--tx2`, and links on `--light` use `--pri-h`.

### Design differences (phase 4), for the owner

- Recommendations ("You may also need", "Frequently bought together") are left out: outside the MVP (ADR-002).
- Delivery step: no "Pick up at our store" option and no delivery method choice (store pickup is not in the requirements or the backend); no Province field (the district comes from the delivery zones); no delivery-day estimates ("Arrives Tue 27 – Wed 28 Oct", "1–2 days"): there is no data for them. The zone box links to the contact page.
- Contact step: no "Send me WhatsApp updates" checkbox (notifications, module 17, are not built).
- Payment step: no card option (disabled, §7 Q21). The MoMo / Airtel number is the contact phone, shown read-only (the backend requests payment from the order's phone). The security note drops "or card number", and the cart's "Secure checkout · MoMo · Airtel Money · Cash" line drops Card.
- Review: no "1-year manufacturer warranty" line per item and no VAT amount before the order is placed (the backend works out VAT when it creates the order; the confirmation page shows it).
- Payment waiting: no "Resend request" button (the backend returns the request already started) and no "the SMS we sent has a link back here" line (no SMS yet). The countdown is the stock hold (15 minutes for mobile money). "Dial *182*7*1#" shows for MTN only.
- Payment failed: the reason is the request's outcome (declined, cancelled, expired); the provider's own reason is not exposed. No "Get help on WhatsApp" button until the contact settings exist (module 19, as in the footer).
- Confirmation: no "We sent an SMS with your tracking link" line (no SMS yet) and no delivery dates. "Create account" links to the registration page with the name and phone filled in, instead of a password field on this page (owner decision 2026-10-27). "Download invoice" shows for signed-in customers once paid. Cash on delivery orders read "your order is placed" and "Pay on delivery".
- Checkout footer: no "Help on WhatsApp" link (module 19).
- Phones keep the stacked layout: the order summary sits below the step (not a collapsible "Order summary (2 items)"), and the step's button stays at the end of the form. The cart keeps the store header with a fixed total and "Proceed to Checkout" bar instead of the tab bar.

## Frontend phase 5 (2026-10-28)

- **Sign-in and registration** (`/login`, `/register`) post to `/api/auth/login|register`, which keep the session token in the httpOnly cookie. `returnTo` is followed only when it is a path on this site (`safeReturnTo`: no other origin, no `//`, backslash or control characters); the default is `/account`. Staff go to `/admin`. With `wishlist=<product id>` (a guest's heart click) the product is saved after sign-in, best effort, before returning. `/register?name=&phone=` fills in the guest's name and phone from the confirmation page; the order stays a guest order. The browser checks the backend's password rule (8+ characters, upper and lower case, a digit or symbol) and shows a four-bar meter.
- **Password reset** (`/forgot-password`, `/reset-password`): the identifier is carried to the reset page in `sessionStorage` (this tab only, never in the URL); opened directly, the reset page asks for it. "Resend" waits 60 seconds. A successful reset goes to `/login?reset=1` ("Password updated").
- **Account area** (`/account/**`): one layout with the side navigation and a client-side gate (guests go to sign in and back, staff to the admin); the backend enforces ownership on every call. Pages read through the proxy with TanStack Query. The order page opens an order by its number (`GET /customers/me/orders/number/{n}`, added for this phase); "Write a review" asks for a single-use link and opens `/review/{token}`. Order lines now carry their item `id`, the public `product_slug` and `reviewed`.
- **Change password and log out everywhere** (owner decision 2026-10-28, ADR-006): `POST /auth/change-password` through the proxy (other sessions end, this one stays); "Log out everywhere" posts to `/api/auth/logout-all`, which calls `POST /auth/logout-all` and clears the cookie (the proxy refuses that path, like logout).
- **Track** (`/track`) uses `POST /orders/lookup` with the order number and phone; `?order=` fills in the number (the confirmation page links with it) and a phone kept for that order in this tab is filled in too. The progress steps (placed, paid or confirmed, packed, out for delivery, delivered) come from the order status and its history (`src/lib/order-progress.ts`), shared with the account's order page.
- **Write review** (`/review/[token]`): the token page is `noindex` and `no-referrer`. States: form, thank you, expired, already reviewed, and an unknown link. The form is covered by a component test with the API mocked (a delivered order cannot be made from the browser tests, since staff deliver orders); the unknown-link state by Playwright.
- **Testing note**: Next.js keeps recently visited pages in the DOM, hidden. Playwright locators use roles or `filter({ visible: true })` so a hidden copy of an earlier page (e.g. the register form) does not match. Every run places real orders in the dev data, so the checkout and account tests no longer use a fixed product (it sold out): `e2e/helpers.ts` `stockedProduct` asks the public catalogue for the cheapest one-variant product still "in stock" and below the free-delivery amount. Abandoned test orders hold stock until `scripts/expire_reservations.py` releases them.

### Design differences (phase 5), for the owner

Owner decision 2026-10-28: features with no backend data are left out until their modules exist.

- Login: no "Keep me signed in" (sessions last 7 days, ADR-006). "Continue as guest" shows only when sign-in was opened from the cart or checkout.
- Register: no "Preferred language" and no "Send me deals by SMS" (no stored preference or marketing consent yet). The phone is required and the email optional, as drawn. The strength help follows the backend rule ("upper- and lower-case letters and a number or symbol").
- Forgot password: no "Send by SMS / Send by email" choice: the code goes to what was typed (a phone gets an SMS, an email an email).
- Track: no arrival time, rider name and phone, or delivery code (no delivery-assignment data), and no "WhatsApp us" button (no contact settings, module 19). The timeline has no "Payment confirmed" time for mobile money (the payment time is not exposed); cash orders show "Order confirmed".
- Account overview: no "On the way", "Delivered" and "Waiting for your review" counts (the order list has no status counts), no product thumbnails on order rows (the order list has no images), and no "Language" in the profile card.
- My orders: no search box and no status tabs (no search or status filter in the order list), no thumbnails, and "Write a review" is on the order page only.
- Order page: no "Warranty until …" per item, no payer phone or payment reference, and no "Need help?" WhatsApp button. The invoice button shows once the payment has succeeded. Cancelled orders show a note instead of the steps.
- Addresses: the "Outside Kigali · RWF 5,000 delivery" badge is "Outside our zones" (delivery is to the three Kigali districts only). Deleting asks for confirmation in a dialog.
- Profile: no "Language" select and no Notifications toggles (module 17); the email is shown read-only (it cannot be changed), and the phone has no SMS confirmation code (not built: "Changing it sends a confirmation code by SMS" is left out).
- Write review: no photos and no display name (the backend stores text only and shows "First name L."); no "Order #… · delivered …" line and no "1 of 2 products" (a link is for one item). The review text needs 20 characters, as drawn. The expired state says links last 90 days after delivery (the backend's rule), not 30.
- Phones: the account navigation sits above the page as a wrapping row of links.

## Frontend phase 6, admin (2026-10-28)

- **Access**: the admin layout reads `/staff/me` and `/staff/me/permissions` on the server (no session → sign in, a customer session → a notice). The sidebar shows only the items the role's permissions open (`src/features/admin/nav.ts`), and every page checks its area again on the server (`AdminPage`), showing AccessDenied with the roles that can open it. `role-permissions.json` is a copy of the backend's `ROLE_PERMISSIONS` for the role table and the AccessDenied text; `backend/tests/unit/test_frontend_role_copy.py` fails when they drift. All of this only decides what is shown: the backend checks every call.
- **Data**: admin screens read and write through the `/api/backend` proxy with TanStack Query; uploads (`postFiles`) send `FormData` through the same proxy. Prices, totals and stock are always the API's; forms send whole-RWF amounts (`parseAmount`, the backend's MAX_MONEY_RWF) and the backend validates again. Filters and pages live in the URL. Stock adjustments send one `Idempotency-Key` per dialog. Promotion and banner dates are sent as Kigali local days; the form shows the last valid day, the API keeps the exclusive end (`endFromDay`).
- **Backend additions for this phase** (owner approved 2026-10-28): staff order list fields and filters (customer, payment method, `q`), `GET /staff/orders/assignees`, `GET /staff/categories` and `/staff/brands` with product counts, product list SKU, price and stock with a `low_stock` filter, and `PUT /staff/products/{id}/images/order` (one transaction).
- **Accessibility**: a table's horizontal scroll wrapper takes keyboard focus (axe `scrollable-region-focusable`: on a phone a wide table with no links could not be scrolled from the keyboard); this applies to every `Table`. The wrapper is also `relative`: screen-reader-only text in cells is absolutely positioned and, without it, widened the page past 390 px so phones zoomed out.
- **Screens without a design** (Product photos bulk upload, Homepage banners) are built from the Import and Promotions patterns and await the owner's approval.
- **Tests**: `src/features/admin/admin-helpers.test.ts` covers the helpers; `e2e/admin.spec.ts` opens every screen as an administrator (axe, screenshots at 1440 and 390 px), and checks the Sales and Finance sidebars and AccessDenied. It saves nothing and needs `E2E_STAFF_PASSWORD` (the seed staff password), otherwise it is skipped.

### Design differences (phase 6), for the owner

Owner decision 2026-10-28: what has no backend data is left out until its module exists.

- Shell: below 1024 px the sidebar is a drawer behind a menu button. "Product photos" (bulk upload) is an extra Catalogue item. Analytics, Reports and Notifications are not in the sidebar (modules 17, 18).
- Dashboard: no revenue, customers, sales chart, top categories or best sellers (no reporting API, module 18).
- Orders: the tabs follow the order statuses; no zone filter, CSV export, row checkboxes, internal notes, staff name in the history, SMS line, or payer phone and reference.
- Orders, Quote requests, Service requests, Reviews and Support share one inbox layout (owner, 2026-11-18; `features/admin/inbox.tsx`): status cards with counts that filter the table, a table of records with WhatsApp and Open on each row (calling is in the drawer, owner 2026-11-18), and a side drawer with the record's details and actions; only the open row is highlighted. The order drawer reads `GET /staff/orders/{id}` and keeps the full page's actions and permission checks (next step, assignment, cancel with a reason, delivery note, invoice); `/admin/orders/[id]` stays and is linked from the drawer, the dashboard and Payments. Quote requests and Reviews replace the list-and-detail split; a quote request still moves by clicking a step, and a review is approved, or hidden with a chosen reason, from its drawer (reviews have no phone, so their rows have only Open). Support shows its conversation in the drawer with the reply box pinned to the drawer's bottom; WhatsApp and Call appear only when the customer gave a phone, and the "Close" action is named "Close conversation" so it differs from closing the drawer. No endpoint changed.
- Payments: no amount cards, search, date range, export, payer column, webhook event list, or "Confirm cash received" (it only works for delivered orders, so it would mislead in the list).
- Products and editor: no Kinyarwanda tab or meta title (the product has one language), no reviews card (no per-product review filter); variants cannot be deleted from here and variant photos are not shown.
- Inventory: no out-of-stock filter, stock value, last movement, export or photos; the tiles are SKUs and Low stock. The design's reasons are kept: they map to the backend's receipt, inspected return and adjustment, and the chosen wording is saved in the note.
- Delivery: no global COD switch, store pickup, delivery time, "orders in 30 days" or "free over" column (the free-delivery amount is one setting, shown above the zones).
- Promotions: no "Product price cut" (only discount codes exist); the type choice is percentage or fixed amount instead. A fourth tab lists draft and paused promotions so they can be edited. "Applies to" offers all products, a category or a brand (the API also takes products: such promotions show "N selections" and keep them).
- Staff: "Add staff member" with an initial password instead of "Invite" (no invitations), and no "Last active". The role table lists the admin's pages from the real permissions, so it differs from the drawing where the drawing was wrong (e.g. Operations can read Products, Management can read Payments).
- Settings: the Store tab has the invoice seller details and the free-delivery amount (the settings that exist); no store contact, opening hours, announcement bar or review-request settings, and no Policy pages or Reviews tabs (module 19). Homepage banners is its own tab.
- Reviews: no store reply, photos, rating or product filters; no average rating line; the customer shows as the review's display name (no phone). The order links to the orders list searched by its number.
- Audit: the Area filter is the record's entity type; the Action column shows the action code under a readable label, and Change summarises the stored values.
- Import: the file is applied at once (no confirm step) and the tiles show rows read, imported, errors and warnings (no created/updated split).

## Frontend phase 7, support pages and errors (2026-10-28)

## Module 19, settings and content (2026-10-29)

This section replaces the module 19 gaps listed in phases 2–7: the Contact and Policy pages, the WhatsApp buttons, the store contact lines and the Settings tabs are now built.

## Admin language and notifications (2026-11-11)

The owner asked for the language switch and the notification bell drawn in AdminTopbar.dc.html, and chose a full Kinyarwanda admin over keeping it English only.

- **Admin language**: the top bar's "EN ▾" menu switches the whole admin between English and Kinyarwanda. The choice is a cookie, `admin_locale` (`en` or `rw`, path `/admin`, one year, `SameSite=Lax`, not httpOnly as it holds no secret); the admin has no locale in its URL. `src/i18n/request.ts` reads it for admin requests and loads `messages/{en,rw}.json` with `messages/admin.json` or `messages/admin.rw.json`; anything else means English. Because the language is per request, the admin layout provides the messages inside its suspended part, and the shell carries `lang`; `<html lang>` stays `en`. Page titles come from `admin.titles.*`. Dates and money keep their current formats in both languages.
- **Kinyarwanda admin copy** is a draft, like the storefront's: `npm run i18n:review` also writes `docs/frontend/rw-review-admin.md`, and a test fails when the two admin files differ in keys, placeholders or rich-text tags, or when the review file is out of date.
- **Notification bell**: a red count of what is waiting for the signed-in staff member (new orders to confirm, support messages to reply to, new quote requests, reviews to approve), from the same counts as the sidebar's badges and only for the areas their role can open. It opens a list of links to each. It is not the Notifications log (A12, `/admin/notifications`, sent and failed SMS and email), which is still not built; the design links the bell to that page.
