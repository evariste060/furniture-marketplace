# Image storage and serving (module 7; ADR-009)

Status: **development works; staging and production serving are not configured.** Where and how media is hosted is part of the hosting decision (ADR-004, not yet written). This page states what the API already does and what any staging or production setup must provide, so the ADR-004 decision can be checked against it. It does not choose a host, web server or CDN.

## What the API does

- Since ADR-009 (2026-10-25) an upload (product image, category image or brand logo) is validated with Pillow and stored twice under one key (`backend/app/services/image_processing.py`): `MEDIA_ROOT/private/<key>`, the exact upload, never served; and `MEDIA_ROOT/public/<key>`, the public source in the same format (upright, no metadata, longest side at most 2400 px). Keys are `<products|categories|brands|banners>/<id>/<32 hex>-<12 hex>.<ext>`, `<ext>` being `jpg`, `png` or `webp`. The module 7 layout (`MEDIA_ROOT/products/...`) is no longer used or served (2026-10-26).
- Keys are random and generated by the server. A file is never rewritten in place: replacing an image stores it under a new key. Files are written to a temporary name in the same folder and then renamed, so a reader never sees a partial file.
- Every public image URL is `IMAGE_PUBLIC_BASE_URL + "/" + key` (`MEDIA_BASE_URL` is still accepted as the old name). The API returns these URLs in the public catalogue and the staff image routes.
- Only with `APP_ENV=development` does the API serve images itself, at `/media`: `MEDIA_ROOT/public` only (`backend/app/main.py`, `PublicMediaFiles`). `MEDIA_ROOT/private` is never served. With `APP_ENV=staging` or `production` the API serves nothing, and it refuses to start unless `IMAGE_PUBLIC_BASE_URL` is an `https://` URL whose host is not `localhost` or a loopback address (`backend/app/core/config.py`).
- Resizing for display is not done by the API: the Next.js image optimizer does it now, a CDN can later.
- Every stored file has a row in the media registry (`media_objects`, ADR-009 §6). Deleting or replacing an image marks its files `deleting` in the same transaction; the **cleanup worker** deletes them afterwards. A file the worker cannot delete keeps its row with the last error and is retried with backoff; staff see it at `GET /api/v1/staff/media/cleanup-problems`.
- `GET /api/v1/health` reports `checks.storage`: `degraded` when the storage cannot be reached.

## What staging and production must provide

1. **A persistent `MEDIA_ROOT`.** An absolute path on storage that survives redeploys and restarts and is writable by the API process user only. It must not be inside the release directory.
2. **One storage for all API instances.** With more than one API process or host, every instance must see the same `MEDIA_ROOT` (a shared volume), or there must be exactly one instance. Otherwise an image uploaded through one instance is missing on another.
3. **Serving `MEDIA_ROOT/public` at `IMAGE_PUBLIC_BASE_URL` over HTTPS** with a web server or CDN, with:
   - `MEDIA_ROOT/private` never served; no directory listing, no script execution;
   - `Content-Type` from the extension (`image/jpeg`, `image/png`, `image/webp`) and `X-Content-Type-Options: nosniff`;
   - `Cache-Control: public, max-age=31536000, immutable`. This is safe because keys are never reused. The engineering recommendation is to set it, because TC-21 asks for efficient image loading;
   - temporary files (`.upload-*.tmp`) not served. They exist only for the moment of an upload.
4. **A request size limit in front of the API** of at least 5 MB plus 64 KB on `POST /api/v1/staff/products/{id}/images`. A smaller proxy limit would reject valid uploads before the API sees them. The API enforces its own limit in any case.
5. **The cleanup worker running** next to the API (`python -m app.worker`, same `DATABASE_URL` and `MEDIA_ROOT`), so retired files are deleted and failed uploads are swept. Without it, retired files stay on disk (still never served by the catalogue).
6. **Backups.** `MEDIA_ROOT` holds catalogue data that is not in PostgreSQL. It must be backed up with the same schedule as the database and restored together with it (TC-23). A database restore without the matching media leaves images whose files are missing.

## Known limits

- **Orphans.** A file is registered before it is written, so a crash leaves a `pending` row that the worker sweeps after an hour. A file written outside the API (or left by a database restore without matching media) has no row: `python -m app.worker reconcile` lists such files and the worker logs their count weekly. Nothing is deleted automatically.
- **Order history.** `order_items.image_snapshot` is a plain string. Checkout (module 14) does not exist yet, and nothing writes that column today. See "Order history and image deletion" in `docs/qa/module-07-media-acceptance.md` for the decision module 14 must make.
- **Object storage** is not implemented. `MediaStorage` (`backend/app/integrations/media/__init__.py`: `put`, `get`, `exists`, `delete`, `public_url`, `list`, `free_bytes`) has one `local` backend, chosen by `STORAGE_BACKEND`; the planned Cloudflare R2 shape (two buckets, custom domain, image transformations) is in ADR-009 and is not built.

## Decision needed (ADR-004, operations and engineering lead)

Where are product images stored and served on staging and production?

| Option | Impact |
| --- | --- |
| A. Local disk on a single API host, served by the same reverse proxy that terminates TLS | Smallest change: no code change. Requires one API host (or a shared volume) and media in the backup plan. |
| B. Shared volume for several API hosts, served by the proxy or a CDN in front of it | No code change. Requires a shared filesystem and its backup. |
| C. Object storage with a CDN | Needs a new storage backend in `MediaStorage`, credentials and an approved provider. Removes the shared-disk and server backup concerns. |

Engineering recommendation: **A for the MVP** (the catalogue is 100–200 products: at about five photos per product and the JPEG/WebP sizes measured for TC-21, a few hundred MB; PNG photos are much larger, see TC-21), adding a CDN in front of it if TC-21 measurements on the real hosting need it. This is a recommendation, not an approval.
