## Design

- **Events and recipient.** `record_order_event` is called where an order's status changes: `OrderService.change_status` (staff) and `_cancel_unpaid_order` (the expiry job and a late payment success). One row per (order, event, channel); a repeat inserts nothing (`ON CONFLICT DO NOTHING`). §7 Q22: SMS to the order's phone when canonical (`+2507XXXXXXXX`), else email to the order's email, else nothing (logged). Every order stores a phone, so in practice SMS.
- **After commit (transactional outbox).** The row is inserted inside the order's transaction, under a savepoint: it commits with the order change or not at all, and a failed insert is logged and rolled back alone. Nothing is sent inside the transaction. After the response, a background task sends the rows the request recorded; anything it did not finish is picked up by `scripts/retry_notifications.py`. Without the outbox, a row inserted after the commit would be lost if the process stopped in between.
- **Claim and lease.** Delivery handles one notification at a time. A short transaction claims the next due row (`FOR UPDATE SKIP LOCKED`), counts the attempt and sets `claimed_until` (2 minutes); the provider is called at once, with no transaction open, while a helper thread renews the lease every 30 seconds in its own short transactions; a second short transaction stores the result only if `attempts` still equals the claim's (the fencing check). Renewal is fenced the same way, so a stale worker can neither extend nor overwrite a newer claim. A row whose lease ended with no result is due again and its earlier attempt is labelled `outcome_unknown`; one that used its third attempt is closed as `failed` with `outcome_unknown`.
- **Attempts and failures.** `attempts` counts provider calls initiated: it is incremented in the claim, immediately before the call. A failed claim rolls back and counts nothing. If a result cannot be stored, the batch stops and the error is raised (the retry job exits 1); rows not yet claimed keep their attempts, and the unrecorded row is retried after its lease. A process that stops between the claim's commit and the call counts one call that was not made (labelled `outcome_unknown`); that is the conservative direction, so the 3-call limit always holds.
- **Statuses.** `pending` (no attempt finished), `sent` (provider accepted), `failed` (last attempt failed; retried at `next_attempt_at` while attempts remain, final when it is null). `in_progress` in the staff list shows a live lease.
- **Delivery guarantee.** At most 3 provider calls per message. No two calls at once while the sending worker can reach the database to renew its lease; if renewals fail for a whole lease, the next worker may call the provider while the first call is still running. A timeout is never taken to mean "not delivered": after a timeout, a lost result or a stopped worker the outcome is unknown and the next attempt sends the same idempotency key (`notification:<id>`); only a provider with idempotent delivery (`idempotent_delivery`) drops the duplicate. Otherwise a customer can receive a message twice. ADR-005 must establish whether the chosen provider supports it, and its call timeout. A provider call that never returns keeps its row leased (`in_progress`) and its worker busy, so providers must time out.
- **Sanitisation and outcomes.** `last_error` is a code: a provider's own `DeliveryError.code` (lowercase letters, digits, underscores; anything else becomes `provider_error`), which is a refusal by the provider; or an unknown outcome: `timeout`, `invalid_provider_response`, `unexpected_error:<type>` or `outcome_unknown`. The staff API describes the difference on `last_error`. Logs carry notification IDs, order IDs, attempt numbers and codes, never recipients or text. The staff list masks recipients.
- **Providers.** `NOTIFICATION_PROVIDER`: `none` (off: nothing recorded; reset 503), `console` (development only), `mock` (delivers nothing; refused in production; reset 503). Each provider declares `reaches_recipient` (required for reset codes) and `idempotent_delivery`.
- **Password reset.** Unchanged rules (customers only, 6-digit code, 15 minutes, 5 attempts, newest code only, rate limits, identical replies). The code is sent once after the commit through `deliver_reset_code`, which never raises and logs only the error type. Codes are not written to `notification_logs` and never retried: a retry would need the code stored.
- **Retry endpoint.** `POST /staff/notifications/{id}/retry` sets `next_attempt_at` to now under the row lock (no extra attempts), audits, then sends after the response. Refusals: 404 `notification_not_found`; 409 `notification_already_sent`, `notification_attempts_exhausted`, `notification_in_progress` (audited with status `conflict`).

## SMTP provider for development and staging tests (2026-10-31)

Approved by the project owner on 2026-10-31, as an interim step: it does not decide ADR-005, B-1 stays open, and `NOTIFICATION_PROVIDER=smtp` is refused in production.

- **Provider.** `SmtpProvider` (`app/integrations/notifications/__init__.py`), Gmail-compatible: STARTTLS with a verified certificate before credentials or mail, no plain-text fallback, each network operation bounded by `SMTP_TIMEOUT_SECONDS`. Credentials come from the environment only.
- **Recipient.** With `smtp`, order messages go to the order's email address; an order without one is logged as having no usable recipient and gets no message. `console` and `mock` keep §7 Q22 unchanged. Password reset by email works; by phone it answers 503 `password_reset_unavailable` before any account is looked up.
- **Failures.** Stored as fixed codes with no server text or recipient: `connection_failed`, `connection_lost`, `recipient_refused`, `sender_refused`, `message_refused`, `auth_failed`, `tls_failed`, `smtp_not_supported`, `smtp_error`, `channel_unsupported`, `invalid_message`. 4xx refusals are retried within the existing 3 attempts; 5xx refusals end the retries. The order is committed before any send, so a mail failure cannot change it.
- **Duplicates.** The existing guarantees apply: one row per order, event and channel, claims and fencing, and no resend of a sent row. New: a failed QUIT after the server accepted the message counts as sent, and every attempt carries one `Message-ID` derived from the idempotency key. SMTP is not idempotent, so criterion 9f stays blocked: after `timeout` or `connection_lost` during sending, a customer can receive a second copy with the same `Message-ID`.
- **`sent` means accepted by the SMTP server.** It does not prove the message reached the inbox: there are no delivery reports, and a later bounce is not recorded.
- **Tests.** `tests/unit/test_smtp_provider.py` and `tests/integration/test_smtp_notifications.py`, against the fake server `tests/support/fake_smtp.py`. No automated test sends a real email. The project owner reported successful real Gmail delivery tests on 2026-10-31; this does not complete TC-19 on staging.
